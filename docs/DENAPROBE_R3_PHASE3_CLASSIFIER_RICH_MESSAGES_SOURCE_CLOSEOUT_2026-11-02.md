# DenaProbe R3 — Phase 3: Filtering-suspicion detector + native Telegram Rich admin UI
**Date:** 2026-11-02 · **Status:** source-only release candidate; operator activation/field E2E explicitly DEFERRED until *all three phases* are code-complete. No ESP32 flash, isolated Collector restart, real relay responder deployment, NPV/GOST/DNS modification or Telegram production alerts as part of this PR.

## Final architecture
`ESP32 (DPT/2 c/z/h)` → `isolated DPT Collector signed SQLite` → `denaprobe_ingest.detector.evaluate()` (read accepted, fresh DPT2 only; own durable incident/transition schema) → `denaprobe_alerts.tick()` (intent journal) → **existing** NVLBot `cloudzy_rich_transport.RichBotAPI`, native `sendRichMessage`/edit with `rich_message` blocks. There is **no second bot/poller/systemd service or web dashboard**; only current Telegram bot can emit alerts. DPT/1 stays pre-auth-only, ignored by this detector.

## Gate and activation flags
`NVL_DENAPROBE_R3_ENABLED=0` is the default. With this flag disabled, no DenaProbe callbacks advertise a dashboard and **no detector loop or proactive alerts run**. `NVL_DENAPROBE_DB_PATH=/var/lib/denaprobe/telemetry.sqlite3` is a configurable path for the existing, independent Collector's isolated SQLite; never point it at customer/user/bot DB. Separate earlier flags: `PROBE_DEEP_ENABLED=0`, `PROBE_DPT_PROTOCOL_VERSION=1` and Collector `--enable-v2` default OFF. After field acceptance, activate staged versioned sender/Collector and only then authorize manager notifications. Do **not** enable bot flag before data freshness/hardware validation.

## Detection policy — observation is not cause
Read only registered `dpt2_latest` and `dpt2_events` with `history_only=0`, matching current boot, server-owned target revision, sequential q and `monitoring_gap=0`. Use independent direct HTTPS control; direct stage age is recovered from immutable sender-age and signed nested completion uptime. Reject data older than 90s, stale/failed direct control, local Wi-Fi loss, unknown codes, authenticated test absent, false/old ACK or boot continuity gap. No creation of Incidents from silence or historical samples; no auto-recovery from silence or target swaps. Two **new** qualifying q samples are required for open, material class change or recovery, not two scheduler ticks.
- `D0_TCP_UNREACHABLE`: independent `c.s` connect failure 20/21/22, with pre-auth SSH NOT a contradictory PASS.
- `D1_SESSION_FAILURE`: TCP and pre-auth pass; independently authenticated `z.s` session reset, disconnect or channel open failure 20/21/30/31.
- `D2_DATA_DEGRADED`: verified authenticated channel with `z.s=40/41` transfer timeout/incomplete. Mere slowness `z.s=42` is UNKNOWN until a size-calibrated field baseline exists.
- `HEALTHY`: TCP 1, pre-auth 1, authenticated two full data transfers and fresh direct HTTPS control. Pre-auth `SERVICE_ACCEPT_PASS` alone is never full HEALTHY.
- `MONITORING_UNKNOWN`: stale/absent worker, local hotspot loss, old h, invalid host key, auth failure, unregistered key, protocol uncertainty. This is NOT a red filtering alert.
- `RECOVERED`: two fresh healthy samples in the matching target revision, followed by exactly one recovery transition.
The current suspicion is `SUSPECTED` (known local class and healthy direct control) or `INCONCLUSIVE`. Do not claim HIGH_CONFIDENCE or numeric censorship percentages without separately attested healthy relay/server or another operator vantage. **No automatic relay switching, relay-change-event recording, remote commands, or carrier attribution.**

## Durable incident + Rich alert protocol
New standalone DPT SQLite tables: `dp3_states`, `dp3_incidents`, `dp3_transitions`, `dp3_delivery`, `dp3_rich_cards`, `dp3_operator_labels`. No migrations to NVLBot private user DB. One active Incident per device/target/revision, states and evidence sequence. A new target revision **supersedes** prior incident without claiming recovery; record retained. Outbox identity `transition_id:recipient_id`, intent committed **before** external Telegram POST; acknowledged send stores message ID; network-ambiguous sends stored UNCERTAIN and **not automatically resent**; definite rate-limits are retriable. Historical transition replay bounded to recent 5min; class-change alert subject to >=2min escalation cooldown. Delivery failures are local to the notification, never change classification.

## Rich dashboard (Bot API 10.3)
The current admin Programs menu shows `📡 پایش DenaProbe` only when explicitly enabled and active admin in private chat. Use **blocks-only Rich Message**, compact RTL table, controls `🔴 اختلال‌های فعال`, `📋 تاریخچه`, `🔄 بروزرسانی`, `🔎 جزئیات`; footer must contain a useful short related tip. Alert/Recovery cards are also Rich Messages, no HTML/text dashboards. Detail cards show target ID/revision, declared operator label (only if separately configured; SSID is not proof), independently measured TCP/auth/session durations, first and second transfer requested/received bytes, HTTPS and received time when available. Absence means `اندازه‌گیری نشد`; old data explicitly appears old. Incident history paginates.
- Existing NVL authentication checked before callback; recheck **current** administrator ID registry, role and private chat for every callback, plus original acknowledged Rich card message ID. Never trust forwarded message, stale card or callback data. Callback data under 64 bytes. No guest/user access; no usernames/private IP/HMAC/SSH keys in Rich card.
- Uses `cloudzy_rich_transport.RichBotAPI` only, no second Telegram token or poller. `_post_init` starts *one* optional asyncio background task only when flag enabled; `_post_shutdown` cancels it. A read-only UI callback cannot invoke any NPV/Edge/GOST actions.

## Tests, acceptance and release decision
CI runs full `tests/test_denaprobe*.py` plus existing `test_cloudzy_rich_bridge_phase7.py`, compiles 1.5MB main bot without executing it, and checks independent R1/R2 DPT compatibility.
Offline fixture tests include healthy, D0, D1, D2, unavailable Auth, Wi-Fi loss, stale direct control, new target revision, no replayed q, recovery, no stale recovery, Rich RTL/table/footer, authorized/unauthorized callbacks, forwarded card protection, deduplicated Rich notification and UNCERTAIN send.
**Physical gate after all 3 phases:**
1. Stage Core first: backup isolated collector and online SQLite WAL backup; check current `k2`, create independent `v2-` key, register actual target/revision, restricted relay test account and loopback responder; stage DPT/2 gate before sending.
2. Flash ESP32 manually using locally ignored credentials and independently validated host pin; verify constrained heap/stack/worker watchdog and finite LTE data budget; verify raw h/c/z statuses and signed ACK.
3. Run known-healthy and replay D0/D1/D2/UNKNOWN/recovery on real operator networks; ensure no stale false-positive, request dedupe, continuity, 90s alert target *measured*, not guaranteed, and appropriate no-signal behavior.
4. Enable `NVL_DENAPROBE_R3_ENABLED=1` only after operator signoff and Telegram iOS+Android Rich rendering/RBAC review. Run no user-facing bot/production changes earlier.
5. On regression disable only the new flag and Collector --enable-v2, restore isolated backup or known-good firmware; NEVER touch `nvlbot.service`, `gost.service`, user accounts, default relay, DNS or customer database as an automatic mitigation.
**Source test passing is not equivalent to hardware acceptance or evidence of who caused filtering.**
