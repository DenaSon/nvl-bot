## 1) مسئله و شواهد Production

در 2026-10-29 چند درخواست GET به `https://dash.cloudzy.com/api/v1` با اینکه DNS/TCP/TLS برقرار بود، **تا ۱۵، ۳۰ و گاهی ۴۵ ثانیه هیچ پاسخ HTTP ندادند**؛ مشکل روی Windows PowerShell و Linux Core، هر دو خانواده IPv4/IPv6، و دو Endpoint `/regions` و `/services/{id}` مشاهده شد. درخواست‌های موفق غالباً زیر یک ثانیه بودند. **این داده‌ها Cloudzy/Cloudflare/backend را به‌صورت قطعی مقصر نمی‌کنند**؛ فقط وابستگی حیاتی NVL به یک خواندن ناپایدار را ثابت می‌کنند. افزایش timeout به‌تنهایی راه‌حل نیست.

حادثه مشخص: عملیات `a0b997e06a92ca35` در انتقال `144.172.69.19 → 144.172.69.61` پس از دو batch موفق `200+200` با `CLOUDZY_PROVIDER_UNAVAILABLE` روی `GET /services/{id}` به `HOLD` رسید؛ `68` حساب باقی ماند. با اقدام اضطراری محلی، ۶۸ حساب باقی‌مانده جابه‌جا شد و طبق گزارش اپراتور اتصال واقعی از همراه اول برقرار شد؛ **آخرین Journal رسمی CZ07 هنوز `HOLD, 400/468` است**. بر اساس آخرین شمارش پس از اقدام، `469` حساب فعال مقصد شامل `468` حساب اولیه و `1` حساب جدید است. این اعداد **Snapshot تاریخی حادثه** هستند، نه معیار ثابت اجرا در آینده؛ پیش از هر تغییر دوباره باید از DB زنده خوانده شوند.

در CZ06 نیز ثبت Standby در CZ04A با `DONE` انجام شد، ولی GET بعد از Commit خطا داد و پیام عمومی خطا به کاربر نمایش داده شد. ثبت موفق یک اثر محلی نباید به‌دلیل مشکل مرحله مشاهده بعدی ناموفق تلقی شود.

## 2) تصمیم‌های اصلی و محدوده

1. **Availability first, safety preserved:** شکست موقت API ارائه‌دهنده، عملیات مستقل را قفل سراسری نکند؛ ولی تغییر DNS، انتقال متعارض، حذف Edge دارای کاربر، عدم تطابق هویت و وضعیت نامعلوم تغییرات خارجی همچنان محافظت شوند.
2. **Cloudzy یک Adapter اختیاری است، نه مرجع حقیقت انتقال حساب‌ها.** خرید/حذف/مالکیت VPSهای خریداری‌شده با Cloudzy فقط در مسیر Cloudzy لازم است؛ داده‌های SSH/WG/DNS/حساب از منابع مستقل و کنترل‌شده بررسی شوند.
3. **در Queue و بین batchها هیچ GET تکراری Cloudzy ارسال نشود.** هویت مقصد هنگام پذیرش ابتدایی مسیر Cloudzy با مشاهده معتبر ثبت و Pin می‌شود؛ در ادامه batch، فقط داده‌های زنده شبکه، Host Key، NAT/WG، مسیر، 6G و SQLite بررسی شوند. Timeout provider هیچ‌وقت به‌تنهایی یک batch نیمه‌تمام را `HOLD` دائمی نکند. در صورت تغییر هویت Pin یا شواهد شبکه، توقف امنیتی واقعی لازم است.
4. **دو مسیر ورودی:** `Cloudzy-assisted` و `Manual emergency` به یک موتور مشترک «ثبت Edge → Standby → Cutover → انتقال حساب → تأیید» می‌رسند. مسیر دستی هیچ درخواست Cloudzy API ندارد و هیچ `provider_server_id` یا رسید خرید جعلی تولید نمی‌کند.
5. **لغو، توقف و بستن پرونده متفاوت‌اند:** لغو درخواستِ اجرا نشده، توقف پس از batch جاری، بستن محلیِ عملیات شکست‌خورده و حذف واقعی VPS/بازگشت کاربران معانی جدا دارند. دکمه نباید چیزی را انجام‌شده ادعا کند که رخ نداده است.
6. **UI مدیر ساده و فارسی:** نام‌های داخلی مانند `CZ03`, `CZ06`, `CZ07`, `HOLD`, `6G`, `Phase` و جزئیات توسعه در متن اصلی و دکمه‌ها ممنوع؛ فقط در «جزئیات فنی» نمایش داده شوند.
7. **هیچ تغییر Production در PR مستندسازی انجام نمی‌شود.** استقرار در هر فاز با پذیرش اپراتور و انتشار جدا از Merge.

### مرز مهم «بدون API»

- `Manual emergency` **صفر وابستگی به Cloudzy API** دارد؛ IP و دسترسی SSH از خود مدیر می‌آید.
- برای **حالت مطلق بدون API خارجی**، مسیر اضطراری باید بدون Cloudflare API هم قابل استفاده باشد: اتصال مستقیم به IP جدید و/یا تغییر DNS از پنل بیرونی توسط مدیر + تأیید پاسخ زنده DNS. بات حق ندارد «DNS خودکار انجام شد» اعلام کند. اگر DNS دامنه کاربران باید عوض شود، هیچ راهی برای تغییر DNS ثبت‌شده در Cloudflare بدون دسترسی مدیریتی به خود Cloudflare وجود ندارد؛ این dependency با تغییر دستی در پنل از فرایند بات حذف می‌شود.
- حالت عادی می‌تواند Cloudflare DNS API را برای Cutover استفاده کند، **اما هرگز Cloudzy API را در مسیر دستی صدا نمی‌زند**. انتخاب `DNS automatic / DNS manual` باید شفاف و جدا باشد.

## 3) معماری هدف و قراردادهای فنی

```text
🧩 برنامه‌ها
    └── 🌐 مدیریت Edge
          ├── ➕ سرور جدید با Cloudzy
          ├── 🛟 افزودن سرور دستی
          ├── 🔁 انتقال کاربران
          └── 🗂 عملیات و بازیابی

Cloudzy-assisted ──► Adapter Cloudzy ──┐
                                       ├──► Edge Registry + Evidence
Manual (IP/SSH/password) ─► SSH Adapter┘             │
                                                     ▼
                                             Prepare + Verify Standby
                                                     │
                                                     ▼
                                      Shared guarded Route/Cutover Engine
                                                     │
                                                     ▼
                                 Durable account-cohort migration + Checkpoints
                                                     │
                                                     ▼
                                             Transport VERIFIED/MOVED
                                                     │
                                                     ▼
                                            Business E2E / DONE
```

### منابع حقیقت و داده‌های پایدار

- **Inventory:** `host_pool` + شناسه Edge ثبت‌شده و fingerprint معتبر؛ `provider='manual'` برای Edge دستی و `provider='cloudzy'` برای خرید اتوماتیک؛ مالکیت Cloudzy را برای `manual` جعل نکنید.
- **Routing:** `host_pool.is_default`، `settings.hosts`، `settings.dns_current_ip` + DNS زنده و lease واقعی 6G؛ با هم باید سازگار باشند.
- **Accounts:** `ssh_accounts`، cohort/snapshot اصلی، ledger جابه‌جایی هر حساب و وضعیت واقعی موجود در Core؛ حساب جدید در مقصد **خارج از cohort قبلی** است و نباید موجب شکست شمارش شود.
- **Journal:** append-only events برای هر intent، preflight، SSH provisioning، effect، checkpoint، cancel و reconcile؛ CAS و transactional outbox/نسخه رویداد. تغییر نتیجه یک اثر محلی همراه با event معتبر ثبت شود، نه صرفاً `UPDATE status`.
- **Secrets:** هیچ رمز، توکن، کلید خصوصی یا متن کامل پاسخ خارجی داخل SQLite، Telegram callback، log، crash dump یا Git نوشته نشود.
- **Locks:** keyed by resource و نوع اثر: `purchase intent`، `target adoption/install`، `core route/6G`، `source-target migration`، `provider deletion`. `HOLD` تاریخی برابر `RUNNING` یا مالک lease زنده نیست. برای worker از lease/heartbeat/fencing/version استفاده شود. آزادشدن قفل فقط بعد از اثبات نبود اثر هم‌زمان یا Reconciliation مستند مجاز است.
- **درگاه تشخیص Provider:** نتیجه‌های `PROVIDER_OK`, `PROVIDER_DEGRADED`, `PROVIDER_IDENTITY_MISMATCH`, `PROVIDER_UNKNOWN` از هم جدا باشند. `DEGRADED` اجازه bypass هویت اولیه یا حذف VPS را نمی‌دهد؛ صرفاً ادامه پردازش مستقلی را مجاز می‌کند که هویت آن قبلاً با دلیل معتبر Pin شده است.
- **محدوده دست‌نخورده:** K2/UID Egress، Marzban/V2Ray، حساب و رمز کاربر، پرداخت، 6H auto-failover و سیستم حذف VPS، مگر Adapter سازگاری لازم باشد. هماهنگی با 6G اصلی حذف نمی‌شود.

## 4) UX الزامی مدیر و امنیت فرم

### منو و وضعیت (بدون اصطلاحات توسعه)

منوی «برنامه‌ها → مدیریت Edge»: **«افزودن با Cloudzy»**، **«افزودن دستی (اضطراری)»**، **«انتقال کاربران»**، **«عملیات و بازیابی»**. هر صفحه فقط عنوان، IP/مقصد، پیشرفت واقعی، وضعیت فارسی، یک راهنمای کوتاه و حداکثر ۲–۳ اقدام مرتبط دارد؛ «جزئیات فنی» جداگانه است. موارد بدون اقدام و پیام‌های طولانی آموزشی حذف شوند. برای UI موجود Rich Messages، اصل سادگی و سازگاری با کلاینت واقعی مدیران رعایت شود؛ نمایش خطا هرگز state اجرا را تغییر ندهد.

وضعیت‌ها: `در حال آماده‌سازی`، `آماده آزمایش`، `آماده انتقال`، `در حال انتقال (x/y)`، `توقف موقت`، `نیازمند بررسی`، `انتقال حساب‌ها کامل`، `تأیید نهایی سرویس`. از نشان‌دادن موفقیت قبل از پذیرش واقعی پرهیز شود.

### فرم دستی دقیقاً با سه فیلد اصلی

1. **IP سرور**: IPv4 معتبر عمومی؛ رد IP خصوصی/loopback/link-local/multicast و آدرس Core یا Host تکراری.
2. **پورت مدیریت SSH**: عدد صحیح 1…65535، پیش‌فرض 22؛ با **پورت اتصال مشتری** تفاوت دارد. پورت مشتری/TLS و Core WireGuard از تنظیمات معتبر Core خوانده می‌شود.
3. **رمز SSH مدیر سرور**: فقط برای Bootstrap؛ **هرگز روی دیسک، DB، لاگ، callback، آرشیو عملیات یا پیام تأیید ذخیره نشود**.

**تصمیم امنیتی:** فرم سه‌فیلدی به‌صورت HTTPS کوتاه‌عمر و یک‌بارمصرف از دکمه بات باز شود (استثنای محدود فقط برای ورود credential، نه جایگزینی داشبورد Rich). احراز هویت و دسترسی با شناسه ادمین، اعتبارسنجی امضای Telegram initData به‌صورت محلی، nonce کوتاه‌عمر، CSRF و محدودیت IP/port/attempt. Password فقط در حافظه RAM Worker با TTL کوتاه، مصرف یک‌باره و پاک‌سازی best effort بماند؛ هرگز Password را در پیام متنی تلگرام درخواست نکنیم، چون حذف پیام ضمانت حذف اطلاعات از Telegram نیست. نبود HTTPS امن/امکان احراز هویت = غیرفعال‌بودن فرم، نه fallback ناامن. UI بات همچنان نقطه ورود این فرم است.

پس از SSH connect: **پین و تأیید مستقل اثرانگشت Host Key پیش از ارسال رمز/اجرای دستور**؛ ترجیحاً اثرانگشت از پنل VPS/کنسول مدیریت مستقل با مدیر تطبیق داده شود. SSH handshake با کلید host ناشناخته نباید صرفاً AutoAddPolicy شود. فقط Ubuntu 24.04 و دسترسی root/sudo قابل‌اعتماد مجاز؛ اگر متفاوت بود پیام فارسی اقدام‌پذیر نمایش داده شود. bootstrap پس از یک‌بار ورود رمز می‌تواند کلید اختصاصیِ محدود به عملیات را روی سرور آماده کند، بدون نگهداری رمز. هیچ shell interpolation یا چاپ رمز در command line.

### دکمه‌های عملیاتی و قرارداد معنایی

| وضعیت واقعی | دکمه اصلی | اثر مجاز |
|---|---|---|
| فرم/درخواست شروع‌نشده | «انصراف» | بدون اثر شبکه/مالی |
| نصب یا انتقال در حال اجرا | «توقف پس از مرحله جاری» | ثبت intent؛ توقف در مرز امن، بدون قطع عملیات نصفه |
| نصب کامل ولی Standby تأیید نشده | «بررسی و ادامه همین سرور» | read-only evidence سپس تنها ادامه idempotent مجاز |
| خطای API ارائه‌دهنده | «ادامه با بررسی مستقل» | فقط با هویت Pin شده و preflight واقعی، بدون Provider POST |
| انتقال ناقص | «ادامه باقی‌مانده» | محاسبه از DB + cohort؛ بدون اجرای مجدد batch موفق |
| عملیات بی‌اثر و قابل بستن | «لغو و بستن پرونده» | CAS+audit؛ آزادسازی scope مربوطه، نه حذف VPS |
| عملیات دارای اثر خارجی نامشخص | «تعیین تکلیف عملیات» | محاسبه اثر و انتخاب اقدام؛ عدم ادعای لغو واقعی |
| انتقال فنی کامل | «ثبت تکمیل انتقال» | `MOVED`، نه `DONE` تا CREATE/RENEW/client تأیید شوند |

لغو حتی در حالت API قطع قابل *درخواست* باشد و در غیاب side-effect/worker به بستن محلی برسد؛ دکمه «لغو» هیچ‌وقت VPS فعال یا کاربران را خودسرانه حذف/برنگرداند. تمام تأییدهای اثرگذار admin-only، دارای nonce یک‌بارمصرف و expiration، audit و CAS باشند.

## 5) برنامه اجرا — دقیقاً پنج فاز

### فاز ۱ — مشاهده‌پذیری، خواندن مقاوم و قفل‌های محدود

**تحویل:** تفکیک `Timeout/HTTP 401/403/429/5xx/TLS/DNS` و تله‌متری امن latency/endpoint/attempt؛ Retry کوچک و محدود *فقط* برای GET/HEAD با backoff و سقف زمان، بدون retry کور POST/DELETE؛ یک لایه تشخیص `PROVIDER_DEGRADED`. شناسایی و جداسازی lock scopeها، نمایش مالک/lease/اثر مربوطه و رفع وابستگی عملیات نامرتبط به `HOLD` تاریخی. ایندکس‌های partial global به‌صورت Migration افزایشی و سازگار، بدون ازبین‌بردن داده، اصلاح شوند. Lock واقعی 6G و محافظ‌های امنیتی حفظ شود.

**فایل‌های اصلی:** `cloudzy_service.py`، `cloudzy_operation_coordinator.py`، `cloudzy_quick_edge.py`، بخش‌های lock در CZ04A/CZ04B/CZ07، Migrationها.

**پذیرش:** خطای GET هیچ POST دوباره تولید نکند؛ خرید مستقل با خرید HOLD نامرتبط قابل شروع باشد؛ یک تغییر DNS هم‌زمان همچنان رد شود؛ 401/403 bypass نداشته باشند؛ تست بازگشت به نسخه قدیمی روی clone Schema قبل از Production بررسی شود.

### فاز ۲ — رفع وابستگی API از صف‌ها و Recovery واقعی

**تحویل:** CZ04B و CZ07 در کل batch loop **هیچ Cloudzy GET** نزنند؛ identity اولیه فقط در مرز پذیرش Cloudzy و با Binding معتبر Pin شود. برای batchها probe شبکه/SSH/WG/NAT، DNS زنده، lease/route و DB CAS بماند. Resume از Journal+cohort با کشف `remaining` واقعی؛ حساب جدید مقصد جدا شمرده شود. مسیر `HOLD → RECONCILED → VERIFYING → MOVED` با Audit و شواهد مستقل موجود شود؛ `DONE` فقط پس از CREATE/RENEW و client acceptance معتبر.

**حادثه جاری:** Job `a0b997e06a92ca35` با `HOLD 400/468` را **قبل از reconcile مجدداً از DB زنده بخوانید** و انتقال ۶۸ حساب خارج از موتور فعلی را با Audit و Cohort reconcile کنید؛ `469` حساب مقصد نباید ۴۶۹ انتقال تاریخی تلقی شود. از مستقیم `UPDATE` کردن status بدون ثبت رویداد و بررسی 6G/DNS جلوگیری شود. سرویس واقعی مشتری مستقل از وضعیت Journal ارزیابی شود.

**فایل‌ها:** `cloudzy_cz04b.py`، `cloudzy_cz07_queue.py`، `cloudzy_cz07_acceptance.py`، `cloudzy_unified_native.py`، ماژول جدید reconciliation.

**پذیرش:** شکست GET پس از batch 200/400، قطع Worker، تغییر تعداد حساب‌های مقصد، انتقال دستیِ باقیمانده و اجرای مجدد همان callback، هیچ‌کدام انتقال تکراری یا قفل بی‌بازگشت نسازند. `MOVED` به معنی تنها تکمیل ثبت انتقال است؛ گزارش `DONE` بدون گواهی E2E ممنوع.

### فاز ۳ — افزودن دستی Edge و آماده‌سازی تا Standby بدون Cloudzy

**تحویل:** ورودی روشن در **برنامه‌ها**، فرم امن سه‌فیلدی IP/SSH port/password، validation و SSH host fingerprint approval، اتصال واقعی SSH از Core، بررسی Host ناشناخته/تکراری، نصب Legacy Edge با Worker معتبر و کنترل‌شده، WG + DNAT/NAT + service port + TLS port + ACL و preflight، ثبت `manual` Edge با Identity مستقل و Evidence، فعال‌سازی Standby. از منطق اصلی Legacy قابل‌استفاده مجدد بهره ببرید؛ نصب موجود را کورکورانه دوباره اجرا نکنید؛ APT lock را محدود منتظر بمانید و از Checkpoint فقط در صورت idempotency اثبات‌شده ادامه دهید.

**فایل‌های اصلی:** adapter جدید `manual_edge_*`، تنظیمات/اتصال اصلی بات، provision/verify موجود، `setup_edge_relay.sh` (صرفاً با refactor و تست)، unified Edge Registry و UI.

**پذیرش:** با **توکن Cloudzy حذف/نامعتبر/قطع**، سرور Ubuntu 24.04 تازه با IP/port/password معتبر از Core به Standby سالم برسد؛ هیچ Cloudzy endpoint فراخوانی نشود؛ رمز در DB/log/Telegram ثبت نشود؛ SSH host key تعویض‌شده نصب را متوقف کند؛ ناموفق‌شدن Telegram UI باعث تکرار installer نشود.

### فاز ۴ — مسیر اضطراری انتقال مشترک و بدون API ارائه‌دهنده

**تحویل:** از Standby دستی، نمایش Preview `source → target`، کاربران واجد شرایط، پورت مشتری و وضعیت DNS؛ انتخاب explicit «DNS خودکار» (در صورت سالم‌بودن Cloudflare API) یا **«DNS دستی/اتصال مستقیم»** (بدون هیچ API خارجی در بات). برای DNS دستی، بات فقط راهنمای مقدار رکورد مقصد و تأیید مشاهده DNS واقعی را ارائه دهد؛ بدون اثبات هماهنگی route/DNS اجرا نشود. سپس موتور مشترک 6G/route CAS + batch مهاجرت checkpoint شده، توقف امن، ادامه فقط مانده، پیگیری account جدید، تست اتصال واقعی در ISP هدف و `MOVED` را اجرا کند. Edge مبدأ تا پذیرش کامل روشن بماند؛ Rollback مسیر یک عملیات مستقل با approval و preflight باشد.

**پذیرش:** یک انتقال ۴۶۸ حسابی شبیه‌سازی‌شده (۲۰۰+۲۰۰+۶۸) با ساخت حساب جدید وسط کار، قطع Worker، DNS دستی و Cloudzy کاملاً قطع، بدون از دست‌دادن اکانت و بدون دوباره‌کاری پایان یابد؛ تست اتصال خارجی و CREATE/RENEW برای `DONE` مجزا لازم باشد. هیچ API Cloudzy در stack مسیر Manual فراخوانی نشود (spy/assertion).

### فاز ۵ — پالایش UI فارسی، لغو روشن، تست جامع و انتشار کنترل‌شده

**تحویل:** صفحه‌های مدیریتی خلوت با CTA متناسب، «عملیات و بازیابی»، ErrorCatalog فارسی برای همه کدهای surfaced، دکمه‌های لغو/توقف/ادامه با وضعیت دقیق، جزئیات فنی اختیاری، حذف متن‌های توسعه/فاز/کد از UI اصلی؛ مستندات اپراتور و پشتیبانی. یکپارچه‌سازی و تست‌های مهاجرت دیتابیس، OTP/nonce، اعتبارسنجی Web form، تزریق command، لو رفتن رمز، ledger ناسازگار، raceها، گزارش batch، side effects، canary و rollback.

**پذیرش:** مدیر از منوی برنامه‌ها حداکثر در چند گام مسیر اضطراری را آغاز کند، تمام خطاها معنی فارسی و اقدام واضح داشته باشند، و هیچ اقدام مستقلی توسط `HOLD` نامرتبط مسدود نشود. تست در چت سه مدیر/Edge آزمایشی قبل از پذیرش Production. نه حذف خودکار Edge قدیم و نه فعال‌سازی 6H/K2 در این نسخه.

## 6) ماتریس تست غیرقابل‌مذاکره

| سناریو | انتظار |
|---|---|
| GET کلودزی هر ۱۵/۳۰/۴۵ ثانیه Timeout می‌شود | retry bounded، خروجی DEGRADED؛ بدون تکرار درخواست پولی یا توقف صف معتبر |
| HTTP 401/403/429 یا تعویض provider ID/IP | هویت یا مجوز مبهم ⇒ توقف اقدام وابسته به Provider؛ علت فارسی دقیق |
| GET بعد از Commit موفق Standby شکست می‌خورد | بعد از Reconcile از واقعیت DB+SSH، ثبت انجام‌شده حفظ؛ خطای جعلی ثبت‌ناموفق صادر نشود |
| تکرار callback تلگرام و restart بین intent و effect | idempotency، fencing و audit؛ no duplicate batch/installer |
| CZ07 در 400/468 متوقف و حساب جدید مقصد ساخته می‌شود | فقط ۶۸ مانده منتقل شود؛ شمار cohort مستقل از حساب جدید؛ ledger صحیح |
| حذف/غیرفعال‌سازی Edge پیش‌فرض یا دارای مشتری | رد بدون حتی یک تغییر |
| Core/Edge SSH Host Key mismatch | STOP امنیتی، بدون ارسال رمز و اجرای نصب |
| Cloudzy env/token absent | Manual: ایجاد Edge/Standby/انتقال با موفقیت؛ Cloudzy-assisted: خطای صریح |
| Cloudflare API ناموجود در مسیر DNS دستی | دستور دستی + live DNS probe + approval؛ **هیچ ادعای DNS write توسط بات** |
| DNS target ناسازگار با default یا lease 6G فعال | STOP واقعی، بدون bypass |
| متن‌های UI | بدون نام فاز/کد داخلی، فارسی کوتاه + action واضح، جزئیات فنی جدا |
| Secret hygiene | رمز فقط در حافظه با TTL، بدون log/SQLite/Telegram/Git و بدون Shell injection |
| CREATE و RENEW انجام نشده | `MOVED` ممکن است؛ `DONE` ممنوع |

## 7) سیاست اجرای فازها و معیار گزارش

- هر فاز: گزارش تحلیلِ قبل، PR محدود، تست اختصاصی + suite موجود (CZ03/CZ04A/B/CZ06/CZ07/6G/Legacy/K2/Marzban regressions)، بازبینی امنیتی، سند Deploy/rollback، سپس Merge. **Merge به معنی deploy نیست.**
- rollout با Feature Flagهای مستقل، از جمله `NVL_EDGE_MANUAL_ENABLED` و `NVL_EDGE_RECOVERY_V2_ENABLED` (نام نهایی در پیاده‌سازی تصویب شود). امکان disable فوری Worker بدون پاک‌کردن Journal.
- پایش معیارها: MTTR، نرخ API timeout، queued/held age، درصد batchهای ادامه‌یافته بدون دوباره‌کاری، درصد عملیات دارای next action، قطع سرویس ناشی از تغییرات.
- قبل از دست‌زدن به SQLite Production، بکاپ معتبر، مقایسه schema نصب‌شده با source، snapshot DNS/hosts/default/account counts، عدم اجرای worker متعارض و rollback سنجیده؛ هیچ `UPDATE` دستی با نتیجه ساختگی.
- **این سند صرفاً طراحی و برنامه توسعه است.** هیچ خرید Cloudzy، تغییر DNS، نصب Edge، انتقال کاربر، پاک‌سازی Journal یا استقرار در زمان ثبت این سند انجام نشده است.

## 8) Definition of Done کل طرح

1. مسیر Cloudzy در صورت اختلال GET، عملیات مستقل را قفل نکند و در وسط صف به Cloudzy GET وابسته نباشد.
2. هر عملیات قابل بازیابی/توقف/لغو متناسب با وضعیت باشد؛ قفل نامرتبط تاریخی هیچ عملیات مستقلی را مسدود نکند.
3. مسیر دستی از «برنامه‌ها»، تنها با **IP + پورت SSH + رمز** و تأیید هویت مستقل، Edge را تا Standby و سپس با تأیید جداگانه کاربران را انتقال دهد؛ **صفر Cloudzy API**.
4. در حالت DNS دستی، مسیر بات **صفر API خارجی** داشته باشد؛ تأیید DNS و E2E واقعی اجباری بماند.
5. UI فارسی، خلوت، بدون اصطلاحات توسعه، با ErrorCatalog و دکمه‌های عملی و قابل‌فهم باشد.
6. تست‌های حادثه 2026-10-29، بازگشت از خطا، crash و secret hygiene در CI سبز شوند و Edge آزمایشی + تست همراه اول با تأیید اپراتور پذیرفته شود.
